# te-connector

The one connector in this PoC: file-based, with synthetic content.
Replays a fixture of synthesized posts as if it were polling a live
source, publishing to RabbitMQ in the same batch → `content.raw.ingested` →
`source.poll.completed` shape a real connector would use.

## Quick start

```
make start               # container `te-connector` (starts infra first if needed)
make logs
make stop
make test-unit           # in the te-connector:local image, no infra
make test-integration    # in the image, against the stack's RabbitMQ
```

Like every service, it runs in a container (python:3.12-slim + venv) defined
in `../te-deployment/docker-compose.yml`; this Makefile only delegates there.
Settings (batch size, interval, looping) come from `../te-deployment/.env`.

## What's here

- `fixtures/raw_content.jsonl` — CONN-1: ~1,450 synthesized posts across
  Reddit, X, Instagram and TikTok over a 24h span, in `postedAt` order. The
  same seven marketing trends appear on every platform, each starting on one
  and spreading to the others after a lag, so trends can be detected *across*
  platforms: "dupe culture", POV product demos, number-led subject lines,
  founder-voice cold opens, a declining "quiet luxury" trend, a sharp
  late-day "lowercase brand voice" spike, and "girl dinner"-style
  micro-content with **no shared hashtag** (only te-cluster's semantic
  clustering can catch that one). Mixed in: evergreen marketing chatter,
  ~12% off-topic noise for te-normalizer's relevance filter, and exact
  reposts / near-duplicate cross-posts for its dedup step. Every record
  matches the `content.raw.ingested` schema exactly.
- `fixtures/post_texts.py` — the post text, written to read like real posts:
  each trend is one idea said 30–50 different ways by shoppers, creators,
  marketers and skeptics (a shared catchphrase in some posts, none in most),
  so finding a trend takes grouping by meaning. Background chatter borrows the
  trends' vocabulary ("how long should a subject line be?") and the noise has
  look-alikes (food "girl dinner", pet "POV" videos) for the relevance filter.
  The generator hands each trend's posts out evenly and never lets two
  independent posts share the same words (dedup would call that a repost).
- `fixtures/raw_content.labels.jsonl` — ground truth for the same posts
  (trend / evergreen / noise, and which post each duplicate copies), kept
  out of the messages themselves. For checking downstream accuracy.
- `fixtures/generate_fixture.py` — produces both files; stdlib only,
  deterministic per `--seed`. Regenerate with `make fixtures` (runs in a
  `python:3.12-slim` container); tune with e.g.
  `make fixtures ARGS="--count 3000 --days 7"`.
- `fixtures/raw_content_v2.jsonl` (+ `.labels.jsonl`) — a realistic-volume
  replay: ~41,000 posts over the 5 days up to the hour it was generated
  (regenerate for fresh dates), 170–530 an
  hour with a day/night rhythm. About 76% is everyday noise, 14% evergreen
  marketing talk and 6% planted trends; it also carries traps (lookalike
  words, spam, a bot-amplified giveaway, non-English posts) and exact,
  near and verbatim-repeat duplicates. Text comes from
  `fixtures/post_texts_v2.py`, written per persona (shopper, creator,
  marketer, small business, skeptic, brand, press).
  Generated by `fixtures/generate_fixture_v2.py` (`make fixtures-v2`,
  e.g. `ARGS="--days 3 --per-day 4000"`). To replay it, from te-deployment:
  `make up v2` (500 posts / 30 s, one pass; `make reset` first if the
  stack has already seen v1). Under the hood that sets `CONNECTOR_FIXTURE_PATH`,
  `CONNECTOR_BATCH_SIZE` and `CONNECTOR_LOOP_FIXTURE`; any you set yourself win.
  The v1 fixture stays the default; e2e tests and the deck's numbers use it.
- `connector/config.py` — CONN-2: env-var config, no framework.
- `connector/batch_reader.py` — CONN-3: parses the fixture and slices it
  into poll-sized batches. `loop=True` (the default) cycles through the
  fixture forever once exhausted — see "no poll-state tracking" below.
- `connector/publisher.py` — CONN-4: thin `pika` wrapper (connect,
  publish, retry once on a dropped connection).
- `connector/main.py` — CONN-5: the poll cycle — publish one batch
  to `content.raw.ingested`, then exactly one `source.poll.completed`
  with that batch's `pollCycleId`/`itemCount`, matching the event
  schemas. The main thread only waits; on SIGTERM
  it stops the scheduler after the poll in progress. Every published
  message is logged in full as one JSON line (`make logs poller`);
  `CONNECTOR_LOG_MESSAGES=false` keeps only the one-line cycle summary.
- `connector/scheduler.py` — CONN-6: runs the poll cycle in its own thread
  every `CONNECTOR_POLL_INTERVAL_SECONDS`, fixed-rate (a slow poll doesn't
  push later ones back; missed slots aren't replayed in a burst). One thread
  on purpose: the fixture is in `postedAt` order and pika's blocking
  connection isn't thread-safe.
- `tests/unit/` — fixture parsing, batch-slicing (including the
  wrap-around case), poll-cycle id generation, the scheduler (fixed rate,
  stop, overrun, errors), and the publisher's
  connect/retry logic — all against fakes/mocks, no infra needed.
- `tests/integration/test_integration.py` — runs one real poll cycle
  against RabbitMQ and confirms the batch lands in
  `q.normalizer.content-raw-ingested` and exactly one message lands in
  `q.aggregator.source-poll-completed`.

## One thing intentionally not decided here

A PoC limitation: no poll-state tracking, not even in Redis, since
there's no real source to track an offset against. "Where we are in the
fixture" lives only in `batch_reader.iter_batches`'s in-process generator
— restart the connector and it starts over from the beginning of the
fixture. That's fine for this PoC's replay; it stops being fine the day
this connector talks to an actual live source.
